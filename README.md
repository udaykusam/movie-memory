# Movie Memory

Sign in with Google, save your favorite movie, and get fun facts about it generated by OpenAI.

**Variant chosen: A — Backend caching & correctness.**

## Tech stack

Next.js 15 (App Router) · TypeScript · React 19 + Tailwind · PostgreSQL 16 · Prisma 6 · NextAuth v4 (Google, database sessions) · OpenAI API · Zod · Vitest

## Setup

### 1. Prerequisites
- Node.js 20+
- Docker (for Postgres)
- A Google OAuth client and an OpenAI API key

### 2. Start Postgres
```bash
docker run --name moviedb -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=movie_memory -p 5432:5432 -d postgres:16
```
After a restart, start the same container again with `docker start moviedb`.

### 3. Environment variables
Copy `.env.example` to `.env` and fill it in:

| Variable | Description |
| --- | --- |
| `DATABASE_URL` | `postgresql://postgres:postgres@localhost:5432/movie_memory` |
| `NEXTAUTH_URL` | `http://localhost:3000` |
| `NEXTAUTH_SECRET` | Any random string, e.g. `openssl rand -base64 32` |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | From Google Cloud Console → Credentials → OAuth client (Web). Authorized redirect URI: `http://localhost:3000/api/auth/callback/google` |
| `OPENAI_API_KEY` | Your OpenAI API key |
| `OPENAI_MODEL` | Optional. Defaults to `gpt-5.4-mini` |

### 4. Install, migrate, run
```bash
npm install
npx prisma migrate deploy   # creates the tables
npm run dev                 # http://localhost:3000
```

### 5. Tests and checks
```bash
npm test          # 14 Vitest tests
npm run lint
npx tsc --noEmit
```

## Architecture overview

```
src/
  app/
    page.tsx                 Landing page with Google sign-in; sends signed-in users to onboarding or the dashboard
    onboarding/              Form + server action to save/change the favorite movie
    dashboard/page.tsx       Profile, favorite movie, FactCard
    api/fact/route.ts        POST /api/fact: returns a fact for the signed-in user
    api/auth/[...nextauth]/  NextAuth route
  components/                FactCard, SignInButton, SignOutButton
  lib/
    auth.ts                  NextAuth config (Prisma adapter, database sessions)
    facts.ts                 Variant A logic: cache, lock, fallback
    openai.ts                OpenAI call (10s timeout, no retries)
    validation.ts            Zod schema for the movie title
    prisma.ts                Prisma client singleton
  middleware.ts              Redirects signed-out users away from protected pages
prisma/schema.prisma         User/Account/Session (NextAuth), Movie, Fact
tests/                       Cache and authorization tests with an in-memory Prisma fake
```

**Data model and why it looks this way**
- `User`, `Account`, `Session`, `VerificationToken`: the standard NextAuth tables, used by the Prisma adapter. `name` and `image` are nullable because Google doesn't always send them.
- `Movie`: `userId` is `@unique`, so the database itself guarantees one favorite movie per user, not just the code. `title` is `VarChar(100)`, which backs up the server-side validation at the database level.
- `Fact`: stores `userId` as well as `movieId`, even though the movie already has a user. That way every fact query is filtered by the session user directly (one `where`, no join), which keeps authorization simple and hard to get wrong. `movieId` ties each fact to one specific movie.
- Index on `(userId, movieId, createdAt DESC)`: this is exactly the "newest fact for this user's movie" query the cache runs on every request, so it is a single index lookup.
- `onDelete: Cascade` on every relation: deleting a user removes their movie and facts, and replacing a movie removes its old facts.

**Request flow for a fact** (`src/lib/facts.ts`)
1. Look up the user's movie (404 if none).
2. If the newest fact is under 60 seconds old, return it (`source: "cache"`).
3. Otherwise open a transaction and take a per-user Postgres advisory lock (`pg_advisory_xact_lock`).
4. Check the cache again inside the lock. A request that waited usually finds the fact the first request just created.
5. Call OpenAI, save the fact, return it (`source: "generated"`).
6. If OpenAI fails or times out, return the most recent fact (`source: "fallback"`), or a friendly 503 if there is none.

**Authorization**
- The user id always comes from the server session, never from the request body or URL.
- Every movie and fact query is filtered by that user id.
- Signed-out requests get a 401 from the API.
- Server actions are public endpoints, so the save-movie action checks the session itself instead of trusting the page.

**Input validation**
- The movie title is validated on the server with Zod (`src/lib/validation.ts`): trimmed, then 1 to 100 characters.
- The form's `required` and `maxLength` are only a convenience; the server action validates again before saving.

**Missing Google name or photo**
- No name: the dashboard says "Hi there!" instead of "Hi, name!".
- No photo: a circle with the first letter of the name or email is shown instead.

**Error handling**

| Situation | What the user sees |
| --- | --- |
| Invalid title (empty, only spaces, too long) | A message under the form; nothing is saved |
| Saving the movie fails | "We couldn't save your movie. Please try again." |
| OpenAI fails or times out, older fact exists | The most recent fact, with a note that a new one couldn't be fetched |
| OpenAI fails or times out, no fact yet | "We couldn't come up with a fact right now. Please try again in a moment." (503) |
| No favorite movie saved | Redirected to onboarding (the API returns 404) |
| Not signed in | Redirected to the home page (the API returns 401) |
| Network error in the browser | A message in the fact card instead of a crash |

## Why Variant A

The interesting problems in this app are on the backend: making sure users only see their own data, not spending an OpenAI call on every click, and behaving well when OpenAI is slow or down. I wanted to solve those properly and prove it with tests instead of spending the time on frontend state.

## Key decisions and trade-offs

- **Advisory lock instead of a unique constraint or in-memory lock.** An in-memory lock only works on one server. The Postgres lock works across multiple instances, is scoped to one user so users don't block each other, and is released automatically when the transaction ends, even on a crash.
- **Trade-off: the transaction stays open during the OpenAI call.** The request calling OpenAI holds a database connection for up to about 10 seconds, and each request waiting for the lock also holds a connection while it waits. That is fine at this scale, but under heavy load it could exhaust the connection pool. At scale I would record a "generating" status row and release the connection while waiting for OpenAI, or move generation to a queue.
- **Lock key uses `hashtext(userId)`.** It is a 32-bit hash, so two users could in rare cases share a lock key. That would only make one wait briefly; it can't leak data.
- **POST for `/api/fact`.** The endpoint can create data and spend money, so it shouldn't be a GET that browsers, crawlers or link previews might call. Responses are not cached by the browser.
- **Changing the movie replaces the row.** The old movie and its facts are deleted (cascade) and a new movie is created, so the cache can never return a fact about the previous title.
- **OpenAI timeout of 10s with no retries.** This keeps the lock short. The user gets the fallback fact instead of waiting.
- **Middleware checks only for the session cookie.** With database sessions it can't query Postgres. It is a fast first gate only; every page, server action and API route validates the session against the database.
- **Database sessions instead of JWT.** Signing out deletes the session on the server.

## Tests

`tests/facts.cache.test.ts` (9 tests): generating a fact, using the cache under 60 seconds, the exact 60-second boundary, using the newest fact, **three concurrent requests producing exactly one OpenAI call**, fallback on OpenAI failure, 503 with no fallback, and 404 with no movie.

`tests/facts.auth.test.ts` (5 tests): never returning another user's fact, every query filtered by user id, no fallback to another user's fact, 401 without a session, and the API serving only the session user's fact.

Tests use a small in-memory fake of the Prisma methods the fact service uses (`tests/helpers/fakePrisma.ts`). Its queries really filter by `where`, and its `$transaction` runs transactions one at a time to simulate the advisory lock. **Limitation:** this simulates the lock rather than testing Postgres itself.
